# Figma Ops: изменение комментариев

Статус: согласовано пользователем 2026-11-03.

## Задача и границы

Добавить в существующий Python CLI Resolve, Unresolve и редактирование текста
комментария. Агент сможет закрывать проверенные замечания и уточнять формулировки,
сохраняя ID комментария, ответы и привязку к макету. Итог — PR в
`YarikMix/agent-utils`, без автоматического слияния.

Изменения выполняются по поручению пользователя; запрос на чтение или проверку
макетов сам по себе не разрешает менять обсуждения. Уже полученное поручение не
требует повторного подтверждения на каждую команду.

Не добавляем остальные возможности figmanage, новый MCP-сервер, npm-зависимости,
автоматическое извлечение cookies из браузеров, изменение дизайна или удаление
комментариев вместо закрытия. Поддержка полного редактирования rich text и
создания mentions не входит: новая команда заменяет текст обычным текстом.

## Рассмотренные подходы

1. **Собственные команды в figma-ops — выбрано пользователем.** Небольшой клиент
   внутреннего API по изученной реализации figmanage, Python stdlib и системный
   curl. Сохраняет автономность плагина; контракт внутреннего API проверяем сами.
2. **Вызов figmanage как зависимости.** Переиспользует команды и авторизацию,
   но добавляет Node.js, отдельный пакет и настройку. Не выбран.

## Предлагаемый интерфейс

```sh
python3 "$FIGMA_OPS_CLI" comment-resolve TARGET --comment ROOT_ID
python3 "$FIGMA_OPS_CLI" comment-unresolve TARGET --comment ROOT_ID
python3 "$FIGMA_OPS_CLI" comment-edit TARGET --comment COMMENT_ID --body-file /path/to/text.txt
python3 "$FIGMA_OPS_CLI" session-login
python3 "$FIGMA_OPS_CLI" session-logout
```

TARGET использует существующий разбор file/branch key и URL. Resolve/Unresolve
принимают только корень обсуждения; ID ответа отклоняется с понятной ошибкой.
Редактирование принимает ID корня или ответа и сохраняет переносы строк UTF-8.
Файл нового текста обязателен; пустой текст отклоняется. Ссылки, ID и входные
данные проверяются до отправки изменения.

Имена команд и способ локального хранения ниже — предложение исполнителя.

## Авторизация

Существующий PAT (`FIGMA_TOKEN`/Keychain) используется для свежего чтения полной
ветки до и после изменения. Веб-сессия применяется только к внутреннему endpoint
на `https://www.figma.com`; PAT туда не передаётся, cookie не отправляется в
публичный REST. Разрешение на изменение определяет Figma для аккаунта веб-сессии.

`session-login` интерактивно принимает значение cookie `__Host-figma.authn`
без отображения ввода и Figma user ID. Сохраняет их в отдельном файле
`~/.config/figma-ops/session.json` с закрытыми правами на поддерживающих их ОС.
Документация объясняет получение значений в авторизованном браузере и ограничения
прав доступа на Windows. Cookie не передаётся через argv, не попадает в историю
команд, ответы CLI, кэш, артефакты, тестовые фикстуры или PR. Сохранение не означает
подтверждения валидности сессии. `session-logout` удаляет только локальные данные
figma-ops, не завершает вход в браузере.

При отсутствии/истечении сессии агент сообщает о необходимости локального входа.
Не ищет запасные cookies и не читает конфиги других приложений. Для живой проверки
автор сообщает пользователю, когда и как потребуется веб-сессия; секрет в чат не нужен.

## Выполнение и подтверждение

Перед записью читается полная актуальная ветка без кэша и проверяется принадлежность
комментария заданному файлу. Resolve/Unresolve с уже нужным состоянием возвращают
проверенный no-op. Аналогично для идентичного текста.

Изученный figmanage использует:

```text
PUT /api/file/{file_key}/comments/{comment_id}
Resolve:   {"resolved_at":"true"}
Unresolve: {"resolved_at":null}
Edit:      {"message_meta":[{"t":"новый текст"}]}
```

Это недокументированный API; форму запроса необходимо подтвердить живой проверкой.
Транспорт передаёт секретные заголовки curl через stdin, проверяет TLS, не следует
редиректам и не повторяет записи автоматически. Ошибки не выводят сырые заголовки
или ответы сервера.

Успех определяется повторным свежим публичным REST-чтением: состояние или текст
совпадает с запросом, ID и принадлежность ветке сохранены. Существующий кэш
комментариев обновляется/инвалидируется, чтобы последующее чтение не вернуло
старое состояние. HTTP 2xx сам по себе не означает подтверждённый результат.
Если после отправки возник таймаут или чтение не подтвердило результат, CLI
сообщает о неподтверждённом исходе; перед повтором требуется перечитать состояние.
401/403/429 не вызывают обход доступа или автоматические повторные записи.

Используем существующий JSON envelope и коды выхода; добавляем данные операции,
признак изменения и подтверждения. Успешное сохранение локальной сессии явно
отличается от проверки её работоспособности.

## Изменяемые части и проверки

- CLI, узкий модуль записи комментариев/веб-сессии, повторное использование текущего
  чтения веток и ошибок транспорта без расширения остальных операций на запись.
- SKILL.md, references/comments.md, references/auth.md и README: новые команды,
  разрешённый scope, подготовка сессии и работа с неподтверждённым исходом.
- Версия плагина и каталоги обоих хостов, соответствующие packaging-проверки.
- Тесты переходов Resolve/Unresolve, редактирования корня/ответа, no-op,
  неправильного файла/ID, истёкшей сессии, 403/429, таймаута и неподтверждённой
  записи, отсутствия секретов в argv/выводе и свежести последующего чтения.
- Полный существующий набор тестов figma-ops и запуск установленной копии из
  постороннего cwd. Новые возможности должны оставаться автономными.
- Живая проверка на собственной тестовой ветке комментариев после получения
  веб-сессии: edit, resolve, unresolve с повторным чтением. Проверенные рабочие
  замечания закрываются отдельно в рамках уже полученного поручения.

Если переносится код figmanage, сохранить необходимые MIT copyright/license
уведомления. Ссылки на исходники и результат живой проверки указать в PR;
секреты и персональные данные туда не включать.

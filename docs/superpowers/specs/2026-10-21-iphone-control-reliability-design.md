# Надёжное управление физическим iPhone через Appium MCP

## Поручение и принятые границы

Пользователь 21.10.2026 поручил автономно доработать существующий `iphone-control` по полному SDD через субагентов, выполнить commit/push и открыть PR. Он уходит спать: вопросы реализации решает controller, значимые решения фиксируются. Это явное разрешение пройти подготовку и исполнение без ожидания промежуточных подтверждений; не разрешение менять безопасность машины, публиковать секреты или трогать телефон ночью.

Цель — следующий агент самостоятельно выполняет разрешённую работу на подготовленном Mac, сохраняя единственного владельца телефона, восстанавливая только свою сессию и проверяя реальный результат ввода/перехода. Добавляем обобщённые правила из уже выполненных опытов, без пересказа проекта Облака.

Исходная версия: свежий публичный main `83221b18479f05a5fc88aafb67da5601c382aec6`; `iphone-control` 1.0.0. Исходное обоснование в `SKILL.md`, `references/operations.md`, `references/validation.md`: native наблюдение, осторожный set_value, настройка отдельно, локальный embedded driver без внешнего Appium URL. Эти решения сохраняются. Нельзя превращать диагностический WDA-доступ в штатную замену MCP или ослаблять границы `setup-iphone-control`.

## Требования

### R1. Передача единственного владения

Основной файл даёт короткий протокол: до действий выбрать устройство, владельца и сессию. Перед делегированием исполнителя проверить именно его доступ к нужным MCP tools; наличие у controller не доказывает наличие у worker. При передаче указать устройство, sessionId, context, исходный экран, разрешённые действия и способ возврата владения. Controller и наблюдатели не отправляют команды телефону во время владения worker. Не делегировать физические действия исполнителю без tools. Тогда controller остаётся исполнителем, а worker может анализировать уже снятые безопасные артефакты. Сессия сама по себе не даёт права управлять чужим телефоном; повторный выбор пользователя не нужен, если конкретный телефон уже согласован.

### R2. Восстановление своей сессии

Наличие managed session и `lockstate=false` не доказывают работоспособность XCTest. При timeout/unknown сначала новое наблюдение и точная ошибка. Если ошибка доказывает stale driver, а сессия собственная и владение у текущего исполнителя, допускается ограниченное пересоздание той же сессии с ранее подтверждённым устройством и capabilities. Не повторять бесконечно и не удалять чужую/неясную сессию. Не считать Code 41 всегда stale: при повторной UI-not-authorized ошибке передать точную причину в setup и запросить у человека системное подтверждение. Не менять provisioning, сертификаты, Developer Mode, настройки безопасности, npm или глобальные процессы ради любого timeout. Cleanup только своих ресурсов, восстановление экрана/context по актуальному наблюдению.

### R3. Надёжная замена URL и текста

Tool success не доказывает замену. Нужна последовательность: свежая единственная цель → прочитать текущее значение → штатно очистить разрешённое поле → подтвердить пустоту/placeholder → ввести полный текст адресным способом → подтвердить точное значение → отдельно отправить Go/Return → проверить результат навигации. `text:""` и обычный set_value не обещают очистку и могут дописывать. Не выполнять Return при несовпадении. Не выдумывать clear-field MCP, не отправлять `w3cActions:true` без доказанного фокуса. Наблюдённая кнопка очистки приложения — предпочтительный путь; проверенный endpoint WDA `POST /session/{W}/element/{E}/clear` описывается только в ограниченной диагностической ветке R4 с E из свежего наблюдения той же WDA-сессии. Не переносить element IDs между разными сессиями/контекстами. Если надёжная очистка недоступна, остановить именно ввод и описать блокер, не портить существующий контент. Системный Clipboard UI не повод читать буфер или вводить секреты.

### R4. Локальная диагностика WDA

Вынести в короткую отдельную reference `references/recovery.md`, ссылки из SKILL/operations. Штатный путь остаётся MCP. Диагностика допустима после конкретной ошибки/отсутствующей операции при собственном владении сессией. До HTTP-действий доказать по локальному процессу/порту и read-only status привязку endpoint к своей Appium/WDA-сессии и выбранному устройству. Один `/status` сам не доказывает UDID и владение; нужны подтверждающие текущие сведения. WDA session ID отличается от Appium session ID, порт динамический. Нет фиксированных 8100/исторических портов и ID. Не сканировать сеть, не использовать remote URL без пользователя, не читать env/конфиги с секретами. При корпоративном proxy для своего loopback HTTP клиент может явно отключить proxy для этого запроса, без изменения глобальной сети/VPN. Для HTTP задать конечный timeout. Не обходить policy/permission rejection через WDA. Не обещать внешний Appium HTTP endpoint у embedded MCP. Не добавлять автоматический HTTP helper и установщик: только инструкция.

### R5. Доказательство открытия и StoreKit

Foreground bundle и hidden недостаточны для доказательства результата. Chrome может остаться foreground с нативной StoreKit-карточкой; подтвердить свежими PNG и native XML, например наблюдённой `ProductPageExtension`, не фиксированной локализованной строкой. Разделить: команда доставлена, диалог показан, карточка открыта, URL получен receiver, нужный контент открыт. Уход на Home/таймаут не считать успехом. Для браузерных проб фиксировать closed/held native UI, document identity, focus/user activation, точный receiver URL если доступен; не объявлять экспериментальные интервалы production-детектором. Этот раздел не выбирает продуктовый сценарий и не утверждает поведение всех iOS-браузеров.

### R6. Упаковка и ограничения

Сохраняем имя и trigger `iphone-control`, существующие native/context/geometry/privacy правила, ссылку на отдельный `setup-iphone-control`. Основной файл остаётся коротким; технические детали в references. Обновляем `iphone-control` до 1.0.1 в обоих manifests и обеих marketplace-записях, не меняя версии/поля других плагинов. README отражает новое руководство, без обещания автоматического setup/MCP или live-проверки. Не менять setup-навык, MCP runtime и установленные копии `~/.codex/skills`/`~/.claude/skills`.

В публичных файлах нет личных UDID, team/bundle IDs, исторических портов, путей пользователя, корпоративных URL, приватных XML/скриншотов или логов auth. Для примеров — явные placeholders. Исходные наблюдения обобщить и отделить от гарантий.

## Проверки

До изменения навыка подготовить неизменяемый набор независимых отложенных сценариев и рубрику, затем снять baseline старой версии. Проверять принятие решений, а не совпадения слов. Сценарии не копировать примерами в обучающий текст. Обязательные группы: worker без MCP и конкурентный controller; чужая/неясная сессия; stale собственная и повторный Code41; склейка URL и неизвестный исход Return; два loopback-порта и разные IDs; native StoreKit поверх того же bundle; policy rejection; отсутствие безопасной очистки и cleanup. Включить старые корректные native/context/geometry/setup границы как regression.

Для проверки обновлённого тела использовать свежий процесс на каждый сценарий (предпочтительно `claude -p` с разрешённым только чтением тестового материала). Никаких живых действий: весь test — решения по синтетическим наблюдениям. Убедиться, что процесс действительно прочёл именно выбранную snapshot-версию, а не установленный старый skill или соседний worktree. Рубрика и prompts зафиксированы до правок. Если Claude CLI недоступен/не авторизован, записать точную причину; разрешён fresh Codex CLI с изолированным prompt и no device tools, с явным ограничением, что это альтернативный runtime и не discovery Claude. Не выдавать статические проверки за behavioral/live-проверку. Если обе версии проходят, зафиксировать отсутствие различающего эффекта, не подгонять baseline.

Публикуемый отчёт содержит команды/метод, модель/runtime, размеры N, результаты OLD/NEW, конкретные ошибки и ограничения. Сырые сеансовые JSONL остаются в gitignored workspace; публиковать только очищенные необходимые выдержки. Проверить локальные ссылки, frontmatter, JSON, согласованность версии, diff --check и сохранность чужих marketplace entries. Отдельные независимые task review и whole-branch review сравнивают результат со спецификацией, не только с планом.

Ночная работа не включает новый live iPhone-прогон. Уже наблюдавшиеся приёмы — источник инструкции, не новое доказательство установки/совместимости. Эта граница должна быть явна в validation и PR.

## Структура и завершение

- Изменить `plugins/iphone-control/skills/iphone-control/SKILL.md` — краткий безопасный workflow, handoff, ссылки.
- Изменить `references/operations.md` — точный ввод, результаты и StoreKit.
- Добавить `references/recovery.md` — bounded recovery и диагностический WDA.
- Изменить `references/validation.md` — факты/ограничения и ссылка на свежий отчёт.
- Изменить plugin README, оба manifests и две marketplace-записи версии.
- Сохранить план и очищенный отчёт в `docs/superpowers/plans/` и `docs/superpowers/research/`.

Выполнить в отдельном worktree, без правки старых worktree и установленных skills. Коммиты только по собственным путям; обычный push новой ветки, без force. Открыть обычный PR в личный GitHub `YarikMix/agent-utils`, base main, reviewer/assignee пользователь по доступности. Не merge. PR по-русски: проблема, итоговое поведение, проверки и реальное ограничение без живого прогона. Не отправлять сообщения коллегам и не менять Jira/Confluence.

## Решения controller

- Один связанный docs-only проект; два deliverable: основной workflow/recovery и интерпретация результата/упаковка/validation. Тестовые fixtures — подготовительный этап до production-текста.
- Не добавляем generic Appium HTTP-клиент: подтверждены только ограниченные диагностические операции, цена ошибочного обобщения выше пользы.
- Native worktree tool доступен, но текущая сессия привязана к `~/projects`, который не является git-репозиторием: создание штатным инструментом завершилось `not a git repository`. Использован sibling git worktree нужного репозитория с актуального fetched main.

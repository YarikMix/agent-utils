# Восстановление своей сессии и диагностика WDA

Штатный путь — зарегистрированные Appium MCP tools по [operations](operations.md). Ниже ограниченные действия после конкретной ошибки или отсутствующей операции; это инструкция по диагностике, не автоматический HTTP helper и не гарантированная замена MCP.

## Один ограниченный retry

1. При timeout/неизвестном исходе сначала получи новое наблюдение и сохрани точную ошибку. Managed session в `list` и `lockstate=false` не доказывают живость XCTest. Timeout сам по себе не доказывает stale driver, а неизвестный исход изменяющего действия не разрешает повтор этого действия.
2. Проверь выбранное устройство, владельца управления и происхождение сессии. Только собственную сессию, при исключительном владении текущего исполнителя и подтверждённом stale driver (например, завершившийся driver/invalid session; socket hang up требует установления причины), допустимо пересоздать **один раз**: удалить явно свою `sessionId`, повторно выбрать ранее подтверждённый физический UDID и создать embedded session с ранее подтверждёнными capabilities по [operations](operations.md). Для чужой/неясной сессии остановись и согласуй передачу, не удаляй её и не создавай конкурирующую.
3. После пересоздания проверь устройство read-only info, context, свежие PNG/XML и заново найди элементы. Восстанавливай экран/context только по актуальному наблюдению и в пределах задачи. Повторно не отправляй действие с неизвестным исходом без доказанного основания. Если один retry не помог, останови recovery и передай точную ошибку в `setup-iphone-control`.

Code 41 не означает автоматически stale driver. При повторном сообщении XCTest/UI-not-authorized прекращай пересоздания: передай точный текст в setup. Доступный системный диалог в пределах задачи обработай самостоятельно по свежим PNG/XML; для ввода кода-пароля или Face ID нужен человек. Не меняй provisioning, сертификаты, Developer Mode, настройки безопасности, npm или глобальные процессы ради timeout. Cleanup — только своих сессий/ресурсов и своего тестового текста; при потере владения сначала согласуй передачу. Не останавливай общие MCP/WDA-процессы.

## Локальная диагностика WDA

Внешний Appium HTTP endpoint у embedded MCP не обещан. Прямой WDA HTTP — наблюдённый диагностический приём, допустимый только при конкретной ошибке/недостающей операции, собственной сессии и текущем исключительном владении. Если MCP/среда вернули policy или permission rejection, не переноси запрещённое действие в WDA, другой клиент или инструмент.

До HTTP-действий установи привязку **endpoint → локальный процесс/forwarder → выбранный физический UDID → своя текущая Appium/WDA-сессия**:

- Используй текущие сведения о своём запуске/сессии и ограниченную read-only проверку соответствующего локального PID/слушающего порта, например `lsof` для уже известного PID. Не читай environment, конфиги с секретами и полные приватные логи. Подтверди устройство по текущей информации о своём процессе/USB-forwarder или запуске, связанной с проверенным UDID.
- Сопоставь это с read-only `/status` найденного loopback endpoint и актуальными сведениями своей сессии. Один успешный `/status`, имя устройства или открытый порт сами по себе не доказывают UDID и владение. При нескольких кандидатах без однозначного соответствия остановись; не выбирай первый ответивший.
- Порт динамический; не подставляй исторический порт или session ID. Appium `S` и WDA `W` — разные ID. Получи актуальный `W` из подтверждённого endpoint/ответа своей текущей WDA-сессии; не принимай Appium ID за WDA ID. Если цепочка соответствия неполна, HTTP-изменения запрещены: вернись к MCP/setup с точным блокером.

Проверяй только доказанный свой loopback endpoint: без сканирования сети и remote URL без пользователя. Для каждого HTTP-запроса задай конечные connect/total timeout (например, 3/10 секунд), без бесконечного ожидания и автоматических повторов. Если корпоративный proxy мешает loopback, явно отключи proxy **для этого запроса** (например, параметр клиента `--noproxy` для `localhost,127.0.0.1,::1`); не меняй глобальную сеть, VPN или proxy. Это не разрешение обходить policy.

### Очистка разрешённого поля

Предпочтительна наблюдённая кнопка очистки приложения. При отсутствии безопасной штатной операции и выполнении **всех** условий выше наблюдён рабочий endpoint WDA `POST /session/{W}/element/{EW}/clear`.

Перед ним получи свежие PNG/native XML и заново найди единственное разрешённое поле **через ту же подтверждённую WDA-сессию `W`**, используя фактический API её поиска. `EW` бери из свежего ответа поиска этой WDA-сессии; Appium `elementUUID:E`, ID другой WDA-сессии/контекста или старого наблюдения не подходят. Не угадывай схему поиска/ответа. При невозможности подтвердить свежий `EW` останови ввод.

Ответ clear не доказывает пустоту: повторно наблюдай значение/placeholder, затем вернись к строгой последовательности [замены текста](operations.md#точная-замена-текста-и-url). Для дальнейших MCP-действий получи свежие MCP-наблюдение и ID; не переноси `EW` обратно. Не расширяй эту ветку до произвольного HTTP-управления телефоном.

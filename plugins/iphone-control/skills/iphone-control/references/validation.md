# Проверка и ограничения Appium

Источники: согласованная спецификация и фактические схемы установленного Appium MCP от 19.10.2026. Наличие операции в API отдельно от её выполнения на телефоне.

## Подтверждённая среда и живые действия

По зафиксированной исходной проверке controller: macOS 26.5.2, Xcode 26.6, iOS 26.6.2, Node 24.21.0, Appium MCP 1.97.1, XCUITest driver 12.18.1. Это проверенная комбинация, не минимальные требования и не гарантия совместимости другого Mac.

Подтверждены: создание сессии, PNG, XML, запуск Settings, переход в About, возврат назад и Home. При повторной проверке после idle прежняя собственная сессия оказалась stale (socket hang up). Controller удалил только свою сессию, повторно выбрал подтверждённый физический телефон и создал embedded сессию без переустановки или изменения provisioning. Свежие PNG и XML снова получены. Наличие сессии в list не доказывает живость WDA. После подтверждения пользователем, что телефон свободен, выполнена дополнительная живая проверка. В Settings прокрутка вверх реально сместила список; изменение подтверждено PNG и XML. В пустом поле поиска введено `Bluetooth` через `set_value`: значение подтверждено XML и PNG. Наблюдённая кнопка «Очистить текст» удалила тестовый ввод; свежий XML показал placeholder «Поиск». Поиск закрыт, восстановлен исходный экран Settings → «Основные», затем исходные приложение Chrome и вкладка; foreground подтверждён `query_state: 4` и PNG. Системные настройки не переключались, ссылки исходной вкладки не нажимались. Прокрутка вниз, pinch и прочие жесты не проверены.

Полная первоначальная установка на втором чистом Mac не проверена. Установка MCP, сборка WDA, запуск XCTest и подтверждённое действие на телефоне — отдельные этапы; успех одного не доказывает следующий.

## Обобщённые наблюдения для доработки 21.10.2026

В исходных материалах текущей доработки зафиксированы следующие диагностические наблюдения: native setValue мог дописывать URL, а пустая строка не гарантировала очистку; после подтверждённой очистки требовалась отдельная проверка точного значения. Локальный WDA clear использовался как ограниченный диагностический приём при установленной привязке своей сессии, не как штатная замена MCP. Наблюдалась StoreKit-карточка поверх прежнего foreground браузера с признаком `ProductPageExtension`; bundle, hidden и работа таймера не доказывали получение URL receiver. Повторный UI-not-authorized Code 41 требовал отдельного системного подтверждения, а не бесконечного stale recovery.

Это обобщение ранее полученных наблюдений, а не новый live-прогон, повторная проверка API или гарантия для других версий. Во время доработки 21.10 телефон не использовался, установка и discovery клиента не проверялись.

## Ранее выполненные проверки инструкции

Четыре отложенных сценария управления: новая инструкция дала PASS в 4/4, старая — 2/4. Это reasoning-проверка свежими агентами с явным чтением переданного тела навыка; кэшированное тело было обойдено. Для настройки baseline и новая инструкция проверялись семикейсовыми batch, по одному batch на свежего агента, а не семью независимыми процессами. Baseline уже давал безопасные решения; новая инструкция дополнительно даёт точные воспроизводимые команды. Вопросы внутри batch могли влиять друг на друга; это не строгий независимый TDD-эксперимент и не доказательство эффекта навыка на каждом случае. Проверки работали с фиктивными ответами, без управления телефоном и без изменения клиентских конфигов.

Это проверка поведения инструкции, **не автоматическое обнаружение установленного скилла**. Свежий Claude CLI завершился `Not logged in` с нулевым использованием токенов; discovery по описанию, поштучные пакеты и отсутствие соседнего навыка через CLI не подтверждены. Проверка маршрутизации симулятора в reasoning не доказывает discovery клиента.

Отдельный свежий агент выбрал ожидаемый маршрут в 5/5 случаях по явно переданным реальным descriptions каталога. Это catalog reasoning, не discovery клиентом.

Упаковка публичных плагинов проверена отдельно: оба JSON-каталога, поштучные записи, пути навыков и manifests, синтаксис JSON/TOML примеров, локальные ссылки и штатный validator `SKILL.md`. Статическая проверка не заменяет установку пакета клиентом или live smoke.

## Проверка надёжности 21.10.2026

В [публичном отчёте OLD/NEW](https://github.com/YarikMix/agent-utils/blob/079e52c7f9fc7d07f4923dce57c7b7426a6405c9/docs/superpowers/research/2026-10-21-iphone-control-validation.md) опубликованы неизменяемые сценарии, точные revisions/SHA256, метод воспроизведения и ручная оценка. На десяти отложенных кейсах, по одному свежему Codex CLI процессу на кейс и версию: OLD 7 PASS / 3 PARTIAL / 0 FAIL → NEW 9 PASS / 1 PARTIAL / 0 FAIL; tool calls 0/20. H8 безопасен, но не перечислил отдельно все пять уровней доказательств; первичная PARTIAL сохранена. H9/H10 regression PASS в обеих версиях. Это синтетическая reasoning-проверка явно переданного тела, без нового live, установки или discovery.

Проверенный NEW operational source — revision `c20f52b606a4bb586915616a55a6e7dccb8a13a6`, до дополнения validation результатами. Последующие правки validation описывают доказательства и ограничения, не являются повторным behavioral-прогоном итогового дерева. Claude CLI оставался неавторизованным; альтернативный Codex runtime не подтверждает Claude discovery. Результат одного ответа на кейс не гарантирует устойчивость поведения.

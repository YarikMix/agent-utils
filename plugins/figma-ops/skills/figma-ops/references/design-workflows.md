# Создание и исправление макетов

Загружай для поручения изменить дизайн в Figma. Для чтения, комментариев и реализации UI в коде достаточно соответствующих read-маршрутов в SKILL.md.

## Исправить существующий макет

1. Прочитай полные относящиеся к поручению треды по [comments](comments.md): root, replies, pin и актуальные договорённости. Составь краткую карту «требование → экраны/состояния → проверка». Ответ «готово» — повод проверить результат.
2. Установи точный file/branch и ноды по [reading](reading.md), прочитай используемые компоненты, стили и переменные по [bindings](bindings.md). Для общего компонента установи затронутые instances, overrides, ширины и состояния; изменение определения не доказывает изменение каждого instance. Если меняются посторонние экраны, сузь правку.
3. Для заданной подписи или согласованной локальной правки опора — существующий макет и его дизайн-система; новый поиск стиля не нужен. Если требуется новое дизайн-решение, подключи Refero, как в маршруте создания ниже.
4. Выполни минимальную правку через официальный `use_figma` с актуальным `figma-use` перед каждым вызовом и точным target по [mcp-routing](mcp-routing.md). Используй существующие компоненты и bindings; локальная правка не требует пересоздать экран. Вернись к карте требований и проверь все затронутые варианты, включая поясняющие подписи.

## Создать новые экраны

1. Из поручения и контекста определи назначение, основное действие, платформы/размеры, состояния и место в сценарии. Уточняй только недостающие решения, существенно меняющие результат.
2. Прочитай соседние экраны и доступную дизайн-систему. Загрузи доступный `refero-design` по каталогу хоста: это методика исследования, а не новый обязательный сервер. Для новых решений используй его styles/screens/flows по задаче; запиши источники и конкретные решения, которые адаптируешь. Без live Refero используй предусмотренные skill craft/user references и явно назови фактический источник. Если самого skill нет, сообщи об ограничении и продолжи доступное исследование по данным пользователя, не приписывая его Refero.
3. Зафиксируй опору реализации: существующая дизайн-система либо выбранное по Refero направление. Добавление экрана в продукт не меняет его палитру, типографику и смысл tokens. Список источников без выбранных решений ещё не основание рисовать.
4. Загрузи применимый официальный `figma-generate-design`, затем следуй его текущему workflow. Запись — `use_figma` с обязательным `figma-use` перед каждым вызовом; получение prerequisites и session/file identity — [mcp-routing](mcp-routing.md). Не путай руководство `figma-generate-design` с отдельным инструментом захвата веб-страницы `generate_figma_design`: выбор capabilities определяет актуальное руководство.
5. Собери согласованные экраны из существующих components/styles/variables. Новые сущности и ассеты добавляй по необходимости через доступные штатные tools. Не создавай лишние состояния или страницу References без потребности задачи. Создание экранов в заданном файле не разрешает перенос в другой файл.

## Проверить и отчитаться

Для каждого затронутого варианта заполни результат в карте требований:

| Требование и источник | Экран / состояние | Свежий рендер экрана и читаемая область | Структура / заказанный переход | Итог |
|---|---|---|---|---|
| Согласованная подпись | Точный node ID, ширина и вариант | Файл, фактические размеры, проверенная область | Текст, видимость, bounds и bindings | Выполнено / дефект / не проверено |

- **Картинка:** свежий весь экран проверяет композицию, отдельная читаемая область — детали и соседние элементы. Проверь фактические размеры скачанного PNG и охват. Запрошенный `maxDimension`/scale не доказывает полученное разрешение. Официальный `get_screenshot` подходит при достаточном результате; иначе точная меньшая нода или проверяемый [экспорт](assets.md). Увеличение уменьшенного preview не восстанавливает детали.
- **Структура:** сопоставь текст, видимость, размеры, переносы/обрезку, Auto Layout, component/variable bindings с рендером. Проверка одной ширины или общего компонента не закрывает остальные варианты. Критерии сравнения и partial coverage — [reading](reading.md#сравнение-реализации-с-макетом).
- **Прототип:** если заказан рабочий переход, проверь trigger/actions/destination и фактическое действие доступным способом. Нарисованная кнопка и подпись перехода не доказывают интерактивность. Недоступная интерактивная проверка остаётся явной; не добавляй прототип к задаче только на статичный макет.
- **Отчёт:** назови изменённые экраны, выполненные требования, реальные проверки и остаток. Непроверенные варианты и известные дефекты не превращаются в общий успех по одному превью или ответу студента. Исправления перепроверь свежим рендером.

Ответ в треде и Resolve — отдельные порученные действия по [comments](comments.md): «поправь макет» само по себе их не разрешает. По явному поручению отправь результат по API в исходный root и проверь readback; закрывай только после проверки всего замечания. Уже данное разрешение повторно не спрашивай.

При отсутствии write capability продолжай доступное чтение и подготовку точной правки, сообщив, что макет не изменён. Подтверждённый forbidden останавливает запись: другой транспорт, аккаунт или копия в Drafts не обходной путь. Разрешённое чтение и отдельно порученные комментарии остаются доступны.
